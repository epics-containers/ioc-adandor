## Developer Container

This repository includes a developer container configuration for Visual Studio Code. This allows you to run the Generic IOC locally and debug it. See https://epics-containers.github.io/main/tutorials/dev_container.html.

The developer container runs the `ioc-adandor-developer:latest` image that CI publishes with each full release, named in both `.devcontainer/devcontainer.json` (what the container runs) and `.devcontainer/initializeCommand` (what is pulled or built): change one and the other must follow. Each time the container starts:

- `.devcontainer/initializeCommand` pulls that image on the host. If the pull fails it uses the local image of that name, and if there is none it builds one with `./build`.
- `ibek dev sync` runs in the container. It compares the project folder with the source the image was built from, brings the support module definitions in line and reports anything that needs a rebuild.

A pre-release tag does not move `latest`. A repository that has made no full release from this template has no such image, so its first start builds one locally. Changes merged to main after the last release are not in the image: `ibek dev sync` reports the difference.

An existing container keeps the image it was created from: use "Dev Containers: Rebuild Container" to move it to the image that was pulled. While the container was created from a different image than the one on the machine, usually an older one, `.devcontainer/initializeCommand` and the `ibek dev` commands print a WARNING that says so.

A container starts without the IOC build products when it is created, by the first start or by "Dev Containers: Rebuild Container". `.devcontainer/postCreateCommand` removes `bin`, `lib`, `dbd`, `db` and the `O.*` folders from `ioc/` in the project folder, because they were built against the support modules of another container. Run `make` in `/epics/ioc` to build the IOC: `ibek dev status` says when that is needed. Source files and the `ioc/config` link that `ibek dev instance` makes are kept, and reopening an existing container keeps its build products.

To run the image built from your own tree instead, for example after changing the `Dockerfile` or on a branch that is far from main, create the marker file and use "Dev Containers: Rebuild Container":

```bash
touch .devcontainer/local-build
```

While that file exists each start builds the image with `./build`, which is quick when the layers are cached, instead of pulling it. The build leaves the project folder as it is: `.dockerignore` keeps the IOC build products and the `ioc/config` link out of the image. Delete the file to go back to the published image. Git ignores the file.

## Channel Access

The vscode developer container auto forwards the channel access ports on the loopback interface. If you have channel access clients running on the host machine, you can connect to the IOC by setting the `EPICS_CA_NAME_SERVERS` environment variable as follows:

## Overview

The Generic IOC for Andor CCD cameras, built on the EPICS areaDetector
[ADAndor](https://github.com/areaDetector/ADAndor) support module.

ADAndor is compiled with Shamrock spectrograph support (`WITH_SHAMROCK = YES`),
but the `ADAndor` ibek support YAML does not load `shamrockSupport.dbd` or
`shamrock.template`, so the ibek entity does not create the Shamrock driver or
its records. The entity's `SHAMROCKID` parameter is passed to the CCD driver.

> [!IMPORTANT]
> This IOC requires the firmware and configuration files (the `etc` directory)
> of the proprietary **Andor SDK2** to be available at runtime. The container
> image contains the driver and the SDK2 shared libraries that upstream ADAndor
> redistributes, but **not** these files: they must be provided separately via
> a Kubernetes Persistent Volume Claim (PVC). See the
> [Andor SDK2 Requirement](#andor-sdk2-requirement) section below before
> deploying this IOC to a beamline.

## Andor SDK2 Requirement

### Background

The open-source
[ADAndor](https://github.com/areaDetector/ADAndor) EPICS driver is compiled
into the container image at build time, together with the **Andor SDK2**
shared libraries (`libandor.so`, `libshamrockcif.so`) that the ADAndor
repository redistributes and links against. The SDK's firmware and
configuration files are proprietary and are **not** included in the image.

At IOC start, the driver calls `andorCCDConfig`, which passes a directory to
the SDK; the SDK reads the detector firmware and configuration files from it.
That directory is the `INSTALLPATH` parameter of the `ADAndor.andorCCD` ibek
entity, with the default value:

```
/usr/local/andor2/etc
```

The instructions below mount a PVC holding the SDK files at
`/usr/local/andor2`, so that its `etc` subdirectory is at the default
`INSTALLPATH`.

The IOC container starts without the PVC. An `ADAndor.andorCCD` entity passes
`INSTALLPATH` to the SDK when it initialises its camera, and a camera that
needs the SDK's firmware and configuration files does not initialise unless
the `etc` directory is there.

**Note on SDK Versioning:** The SDK2 libraries in the image are version 2.102.30034.0. Take the `etc` files from an SDK2 release that is compatible with those libraries; use a version recommended by your facility's controls team or hardware vendor.

### Obtaining the SDK

The Andor SDK2 is a proprietary software package supplied by
[Oxford Instruments / Andor](https://andor.oxinst.com/). Contact your local
controls group to obtain an appropriate copy for your facility.

At Diamond Light Source it is maintained in the internal repository
`https://gitlab.diamond.ac.uk/controls/support/andorCCDSDK`, which is
reachable only from inside Diamond's network.

### Step 1 — Create a Persistent Volume Claim

Before deploying an Andor camera with this IOC you must provision a PVC to
hold the SDK files. Add
an entry to your beamline's `epics-pvcs` Helm chart `values.yaml`:

```yaml
epics-pvcs:
  additionalPvcs:
    # PVC for Andor SDK2 firmware and configuration files, needed for the Andor CCD camera to work
    - name: andor-sdk2
      size: 128Mi
```

Deploy (or upgrade) the `epics-pvcs` chart so that the PVC is created in your
namespace before continuing.

### Step 2 — Populate the PVC with the SDK

Because the SDK is proprietary it cannot be fetched automatically. You must
copy the SDK files into the PVC manually, through a pod that mounts it.

The `epics-pvcs` chart deploys a persistent `busybox` pod that automatically
mounts every PVC — including all `additionalPvcs` entries — under `/mounts/<pvc-name>`.
This means the `andor-sdk2` PVC is accessible at `/mounts/andor-sdk2` inside
that pod, so **no separate helper pod is needed** when you can reach it (the
first approach below). The second approach creates a temporary helper pod for
when you cannot.

Whichever approach you use, the root of the PVC must contain:
- `etc/` — detector firmware and configuration files

The IOC does not load any shared libraries from the PVC: it uses the ones in
the image.

#### At Diamond Light Source (using ec-cli)

   If you are working within the Diamond computing environment, use the
   [ec-cli](https://github.com/epics-containers/edge-containers-cli) tool
   to configure your `kubectl` context for the target beamline domain, then
   copy the SDK directly into the `epics-pvcs` pod:

   ```bash
   module load ec/<domain>
   kubectl cp /path/to/local/andor2/. <domain>-epics-pvcs-<pod-id>:/mounts/andor-sdk2/
   ```

   Replace `<domain>` with your services domain (e.g. `i21`) and use
   `kubectl get pods` to find the exact `epics-pvcs` pod name.

#### Generic approach (helper pod)

   If you are not at Diamond, or do not have `ec-cli` available, and the
   `epics-pvcs` pod is not yet accessible, you can spin up a temporary
   `busybox` helper pod to access the PVC:

1. **Spin up a helper pod** that mounts the PVC:

   ```bash
   kubectl run andor-sdk-loader \
     --image=busybox \
     --restart=Never \
     --overrides='{
       "spec": {
         "volumes": [{"name":"sdk","persistentVolumeClaim":{"claimName":"<domain>-andor-sdk2-claim"}}],
         "containers": [{"name":"andor-sdk-loader","image":"busybox",
           "command":["sleep","3600"],
           "volumeMounts":[{"mountPath":"/usr/local/andor2","name":"sdk"}]}]
       }
     }'
   ```

   Replace `<domain>` with your services domain (e.g. `i21`).

2. **Copy the SDK from your local machine** into the PVC:

   ```bash
   kubectl cp /path/to/local/andor2/. andor-sdk-loader:/usr/local/andor2/
   ```

3. **Remove the helper pod** once the copy is complete:

   ```bash
   kubectl delete pod andor-sdk-loader
   ```

### Step 3 — Mount the PVC in the IOC Helm chart

In your IOC service `values.yaml`, add `volumeMounts` and `volumes` entries
so that the PVC is mounted at `/usr/local/andor2` inside the container:

```yaml
ioc-instance:
  image: ghcr.io/epics-containers/ioc-adandor-runtime:<version>

  volumeMounts:
    - name: andor-sdk2-volume
      mountPath: /usr/local/andor2

  volumes:
    - name: andor-sdk2-volume
      persistentVolumeClaim:
        claimName: <domain>-andor-sdk2-claim
```

### Step 4 — Configure the IOC entity

In your ibek `ioc.yaml`, add the `ADAndor.andorCCD` entity. The `INSTALLPATH`
parameter must point to the `etc/` subdirectory inside the mounted SDK volume:

```yaml
entities:
  - type: ADAndor.andorCCD
    P: <beamline-prefix>
    R: ":CAM:"
    PORT: <port-name>.cam
    INSTALLPATH: /usr/local/andor2/etc   # default — change only if needed
    TIMEOUT: 1
```
